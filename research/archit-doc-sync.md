## Each publication check

1. Run `node C:/AI/projects/SportsPlayLLMResearch/scripts/archit-progress-snapshot.mjs --output C:/AI/projects/SportsPlayLLMResearch/artifacts/google-doc-sync-20260906/snapshot-live.json`. It reads the existing runtime on numeric loopback, including the SQL dependency-aware frontier endpoint. It writes no Google content and launches no model, worker, scheduler, or experiment.
2. Read the compact JSON and `state/archit-doc-sync-state.json`. Use its explicit capture time, counts, actual route and last verified evidence identity. A running call is activity, not a result. Never infer progress from timestamps, document count, source rechecks or pending/review backlog.
3. Read the current native Doc and revision even when the runtime semantic hash is unchanged. The managed section must still exist and its text/native-date hash must match `managedContentHash` from the last acknowledged publication. Preserve unexpected collaborator edits and record a reconciliation-needed receipt; do not overwrite them. If both state and managed content match, skip the write. The Doc shows the time of its last changed snapshot; do not claim a newer check was published. On stopped/idle status, publish that status rather than imply agents are working.
4. Use the Google Drive/Docs skills and direct connected Docs APIs. Save the plain native document result locally (not the MCP envelope). Run `node scripts/archit-doc-payload.mjs prepare --snapshot artifacts/google-doc-sync-20260906/snapshot-live.json --document <fresh-doc.json> --state state/archit-doc-sync-state.json --output <request.json>` from this project. Pass only its structured API argument object to the connector; if it returns `skip`, do not issue a write. The helper verifies capture freshness and hashes, constructs native date chips, and replaces only `SOCCER_LIVE_STATUS_V1`. Missing/ambiguous ranges or collaborator changes fail closed. A `recoverAcknowledgment` result means the exact intended payload already exists after an interrupted write; verify its native content and retain an explicit recovery receipt before updating acknowledgment. Keep activity and verified delivery separate; no task instructions or raw output enter the Doc.
5. Use `write_control.requiredRevisionId`. After a conflict, refresh native indexes, recheck the acknowledged managed-content hash, and retry one newly grounded write; never reuse stale offsets or erase an intervening collaborator edit. Read the updated native Doc and run `node scripts/archit-doc-payload.mjs verify --snapshot <same-snapshot.json> --document <after-doc.json> --before <before-doc.json> --output <verification.json> --ack-state state/archit-doc-sync-state.json`. This verifies exact text/native dates and unchanged surrounding content before atomic acknowledgment. Preserve all unrelated state fields. The state retains the last successful runtime snapshot separately from any unavailable-source notification.
6. Scientific text may change only for a versioned candidate with exact-file receipts, an actual independent Luna verdict, all material defects resolved, and a later Terra inspection/promotion decision binding the same content. Confirm actual model and complete candidate exposure; configured names or a clipped review do not count. A full research draft remains unpromoted if only a compact contract was reviewed. Preserve uncertainty and no-performance boundaries. The original user request authorizes these reviewed progress updates in this Doc; it does not authorize footage upload or broader publication.
7. When fresh runtime reads fail, retain the error receipt and do not overwrite the last successful runtime snapshot. Try one materially distinct read-only check of runtime health. If fresh project data remains unavailable and Docs is reachable, load the retained `snapshot-live.json` and use `unavailableSnapshot(lastGoodRuntimeSnapshot, actualFailedCheckTime)` exported by the payload helper. The snapshot helper updates this file on every successful poll, including unchanged polls, and leaves it untouched on failed reads. Thus it is more current than `state.lastPublishedRuntimeSnapshot`, which is only a fallback if that retained file is unavailable. Save a separate failure payload, then use the same prepare/readback path. Its text distinguishes the failed check time from the last successful snapshot and last verified delivery; it makes no current activity claim.
