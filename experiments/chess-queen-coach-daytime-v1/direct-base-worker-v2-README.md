# Direct interpreter launch candidate

The candidate starts the pinned base Python process directly while pointing its local `__PYVENV_LAUNCHER__` value at the existing project environment. It reuses the original worker's exact job constructor and GO bootstrap. The original files are unchanged.

Before GO, the parent checks the actual Popen handle's PID, image and creation time; the creator's identity; explicit membership in the parent-held job; and a complete job list containing only that child. It records the list again after GO. Closure requires the direct child handle to show EXIT and the complete owned job to be empty before releasing the shared lease. Only this owned child/job may be terminated. Every failure retains a receipt where storage permits; a failed observation cannot qualify ownership. Job handles stay in the parent.

The public interface is `run_worker(arguments, receipt, maximum_seconds=300, lock_path=LOCK)` and `--receipt PATH --maximum-seconds N -- SCRIPT ARGS...`. The full script-prefixed vector uses the original `SHA256(json.dumps(arguments).encode())` convention. The deadline bounds the wait after GO; up to 10 seconds of owned cleanup is separate. No resource floor or model procedure changes here.

The separate CPU protocol plans exactly one original launch and one candidate launch, using the same authored metadata payload. It requires exact Python executable, prefixes, ordered search path, flags, site settings, package versions and module locations. Package lookup never imports Torch, Transformers, bitsandbytes, PEFT or python-chess. Actual PIDs/topology and the interpreter/output argument paths are retained separately. The candidate payload must observe itself as the only current-job member, with the parent and actual image matching the parent's pre-GO proof.

Root alone may dispatch the prospective CPU plan after complete source and protocol review. The result is create-only, with all two planned request statuses retained if either fails. A busy lease starts no child. No replay, model call, engine call or scientific source modification is part of the plan. CPU environment parity is an operational gate; separate actual observer, warm-training and cold-generation qualifications plus their independent audits are still required before scientific training.

The motivating original diagnostic is descriptive. It found that its actual venv delegate was outside the explicit creator job on one instrumented launch. It did not establish the cause or frequency, historical ownership state, or a parent-death safety failure. A venv redirector's private job may still have killed that delegate indirectly. This candidate does not rewrite that evidence.

Machine interfaces: worker `schema=chess.owned-worker.v2`, `launch_profile=direct-base-owned-worker-v2`, `source_sha256`, `owned_member_before_go`, `owned_job_exit_verified`, legacy script/arguments/status/exit/lease fields, and `ownership.before_go/closure`. Parity PASS retains `worker_source_sha256`, `protocol_sha256`, `candidate_worker_sha256` (also `worker_sha256`) and `original_worker_sha256`. A future independent actual audit must bind the protocol, closed parity result and candidate worker receipt; no actual audit is fabricated by this software.
